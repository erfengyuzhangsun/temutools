## P0 模块1：API对接与数据同步

### TC-API-001：正常流程-单店铺首次成功同步订单
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已绑定1个有效Temu店铺，API凭证有效，Temu平台有≥1条订单
- **步骤**：
  1. Arrange：准备有效的店铺绑定配置（shop_id=1, api_key, api_secret），模拟Temu API返回1条标准订单数据
  2. Act：调用同步服务 `sync_service.sync_orders(shop_id=1)`
  3. Assert：同步成功返回True；数据库中temu_sync_orders表新增1条记录；同步日志记录"同步成功"

### TC-API-002：正常流程-多店铺同时同步
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已绑定3个有效Temu店铺，均有有效API凭证
- **步骤**：
  1. Arrange：准备3个店铺配置，模拟3个Temu API分别返回不同数量订单（5条/0条/12条）
  2. Act：并行调用 `sync_service.sync_all_shops()`
  3. Assert：3个店铺均同步完成；店铺1入库5条，店铺2入库0条，店铺3入库12条；sync_logs表3条成功记录

### TC-API-003：异常-API密钥无效/过期
- **优先级**：P0
- **测试类型**：异常场景
- **前置条件**：店铺API密钥已过期或无效
- **步骤**：
  1. Arrange：配置过期的API密钥，模拟Temu API返回401错误
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：同步失败返回False；错误日志记录"API认证失败(401)"；触发系统告警通知；不阻塞其他店铺同步

### TC-API-004：异常-网络超时
- **优先级**：P0
- **测试类型**：异常场景
- **前置条件**：网络连接不稳定
- **步骤**：
  1. Arrange：模拟Temu API请求超时（timeout异常）
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：自动重试3次；每次重试间隔递增（5s/10s/15s）；3次均失败后返回False；日志记录"网络超时，已重试3次"

### TC-API-005：异常-服务器500错误
- **优先级**：P0
- **测试类型**：异常场景
- **前置条件**：Temu平台临时故障
- **步骤**：
  1. Arrange：模拟API返回500错误
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：自动重试3次；最终失败返回False；错误日志记录"服务器错误(500)"

### TC-API-006：边界-Temu API返回空数据
- **优先级**：P0
- **测试类型**：边界值
- **前置条件**：店铺无任何订单
- **步骤**：
  1. Arrange：模拟API返回空数组 []
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：同步成功返回True；同步计数=0；日志记录"同步完成，无新数据"

### TC-API-007：边界-Temu API返回大量数据(10000+条)
- **优先级**：P0
- **测试类型**：边界值/性能
- **前置条件**：Temu平台有大量订单
- **步骤**：
  1. Arrange：模拟API分页返回共15000条订单数据（每页500条）
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：全量同步完成；库中准确入库15000条；单次同步耗时不超过5分钟

### TC-API-008：安全-API密钥加密存储
- **优先级**：P0
- **测试类型**：安全测试
- **前置条件**：新绑定店铺
- **步骤**：
  1. Arrange：输入API密钥 "test_api_key_12345"
  2. Act：执行店铺绑定操作 `shop_service.bind_shop(api_key="test_api_key_12345")`
  3. Assert：数据库存储的是加密密文而非明文；解密后可还原原始密钥；日志不打印完整密钥

### TC-API-009：安全-多店铺数据隔离
- **优先级**：P0
- **测试类型**：安全测试
- **前置条件**：存在店铺A和店铺B，用户甲拥有店铺A，用户乙拥有店铺B
- **步骤**：
  1. Arrange：用户甲登录，店铺A有100条同步订单；用户乙登录，店铺B有50条同步订单
  2. Act：用户甲查询全部订单；用户乙查询全部订单
  3. Assert：用户甲只能看到店铺A的100条；用户乙只能看到店铺B的50条；查询接口无数据泄露

### TC-API-010：数据完整性-订单数据字段完整校验
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：API返回标准订单数据
- **步骤**：
  1. Arrange：准备含有全部必填字段的订单数据（order_id, sku, quantity, price, status, create_time等）
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：所有必填字段均被正确入库；字段类型匹配（数值型为float/int，日期型为datetime）

### TC-API-011：数据完整性-字段缺失处理
- **优先级**：P0
- **测试类型**：异常场景
- **前置条件**：API返回的数据缺少某些非关键字段
- **步骤**：
  1. Arrange：模拟缺少"备注"字段的订单数据
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：同步成功；缺失字段在数据库中为NULL或默认值；日志记录"字段[备注]缺失，已使用默认值"

### TC-API-012：增量同步-已有数据不重复导入
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已同步过50条订单，Temu平台新增10条
- **步骤**：
  1. Arrange：数据库已有50条订单（order_id唯一），模拟API返回60条（含50条旧+10条新）
  2. Act：调用 `sync_service.sync_orders(shop_id=1)`
  3. Assert：仅新增10条记录；总记录数变为60；无重复订单报错

### TC-API-013：同步状态-全量同步记录与查询
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已完成至少1次同步
- **步骤**：
  1. Arrange：执行一次同步操作
  2. Act：调用 `sync_service.get_sync_history(shop_id=1)`
  3. Assert：返回同步历史列表；包含同步时间、同步数量、状态、耗时

## P0 模块3：全局定时任务调度中心

### TC-SCHED-001：正常流程-定时任务按周期执行
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已配置数据同步任务，周期=每小时
- **步骤**：
  1. Arrange：注册sync_orders_task，cron表达式="0 * * * *"，当前时间10:00
  2. Act：启动调度中心 `scheduler.start()` → 等待10:00触发 → 监控任务执行
  3. Assert：10:00准时触发执行；任务状态=completed；记录执行日志

### TC-SCHED-002：正常流程-多个任务并行执行
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：已注册3个独立任务
- **步骤**：
  1. Arrange：任务A（周期1min/耗时5s），任务B（周期2min/耗时3s），任务C（周期5min/耗时8s）
  2. Act：启动调度中心，运行10分钟
  3. Assert：任务A执行10次，任务B执行5次，任务C执行2次；任务间互不阻塞

### TC-SCHED-003：正常流程-任务手动启停
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：任务A处于运行状态
- **步骤**：
  1. Arrange：任务A正在运行
  2. Act：调用 `scheduler.stop_task("task_A")`

### TC-SCHED-004：异常-任务执行抛出异常

  2. Act：等待任务触发执行
  3. Assert：任务状态=failed；错误日志记录异常堆栈；调度中心继续运行不影响其他任务

### TC-SCHED-005：异常-任务执行超时

- **测试类型**：异常场景
- **前置条件**：任务配置超时时间=30s
- **步骤**：
  1. Arrange：注册一个执行耗时60s的任务（超时时间30s）
  2. Act：等待任务触发执行
  3. Assert：30s后任务被强制终止；状态=timeout；日志记录"任务执行超时(30s)"

### TC-SCHED-006：正常流程-任务执行日志查询
- **优先级**：P0
- **测试类型**：正常流程
- **前置条件**：任务A已执行过5次
- **步骤**：
  1. Arrange：任务A执行5次，其中1次失败
  2. Act：调用 `scheduler.get_task_logs("task_A")`

### TC-SCHED-007：边界-任务重试机制
- **优先级**：P0
- **测试类型**：边界值
- **前置条件**：任务配置最大重试次数=3
- **步骤**：
  1. Arrange：任务第一次执行失败
  2. Act：等待自动重试
  3. Assert：自动重试3次；重试间隔符合配置（如30s/60s/120s）；3次均失败后标记为失败

### TC-SCHED-008：配置-任务周期动态修改

- **测试类型**：正常流程

  3. Assert：修改后下次触发按新周期15分钟执行；无需重启调度中心
